# The PM bot

For Hermes's place on the production line and a requester's first action, see [Use your client](https://bakers.build/get-started/use-your-client#hermes). This experimental integration has no dedicated Bakers addon.

The PM bot is a project manager for one bakers.build project in Slack, built on [Hermes Agent](https://github.com/NousResearch/hermes-agent). A mention in its main Slack channel opens a public channel for that request. There it runs bakers.build's `bb-create-ticket` skill to specify the request with its requester as a ticket, answers status questions, posts the ticket's state changes, relays agent questions and passes the answers back. The channel is renamed after its ticket and archived when the ticket is finished.

It runs as one container from the image this folder builds, started with [`compose.yaml`](compose.yaml) by a Coder workspace template from workspace parameters. keytec's template is `keytec-coder` in keytec/infra (`coder/templates/keytec-coder/README.md` › PM bot), which also describes the setup.

| Part | What it is |
|---|---|
| `Dockerfile` | The bot's image: the official Hermes image at v0.22.5, pinned by digest, with this folder's content in `/opt/pm-bot`, the shipped skills in `/opt/pm-bot/skills`, and `php-cli` with Composer 2 (pinned by digest) for the nightly audit |
| `build/collect-skills.mjs` | At build time, copies `bb-create-ticket`, `bb-recipe-superpowers` and `bb-recipe-matt` with every bundle file their links reach; refuses a link that leaves the bundle, reaches another skill or is broken |
| `entrypoint.sh` | The container's start, as the `hermes` user: checks the env, renders the configuration, puts the persona and the shipped skills into Hermes' home, runs the poller and the gateway |
| `render.mjs` | Fills the `${…}` placeholders of the configuration and the persona from the env; refuses an unset value or one that could change the YAML |
| `config.template.yaml` | Hermes configuration: Slack, toolsets, approvals, the `clone-reader` MCP server and bakers.build's `/mcp` as the `bakers` server |
| `skills/composer-audit/` | The bot's own skill for the nightly Composer audit: `SKILL.md` is the whole procedure, from the pull marker through `composer audit` to the ticket or comment |
| `SOUL.template.md` | The persona, rendered into `SOUL.md`: the host context `bb-create-ticket` takes (project, workflow, conductor, the requester from Hermes' sender prefix, the channel's link), status answers and passing answers back |
| `plugins/bot-channels/` | A Hermes plugin: turns a mention in the main channel into a request channel, admits only the bot's own open channels, tells the model each channel's ID, link and ticket, and sets the bot's language (`language.py`, the plugin's texts in `messages.json`) |
| `poller/` | Posts state changes, status updates between them and open questions into each ticket's channel; renames, archives and reopens the bot's channels; no LLM |
| `lib/bakers-client.mjs` | The poller's bakers tool calls on `/mcp`, with the API key as bearer |
| `slack-app-manifest.yaml` | The Slack app, created in one step |
| `.env.example` | The keys the container reads from its env file, which the Coder template writes |

The bot's reach is limited by its tools and its container. In Slack it has no terminal, file, browser or web toolset, only a filesystem MCP server that sees only a read-only, secret-free clone of the project's code, and nine of bakers.build's own tools (`bakers_ticket_create`, `bakers_ticket_read`, `bakers_ticket_search`, `bakers_ticket_update`, `bakers_ticket_transition`, `bakers_ticket_classify`, `bakers_comment_create`, `bakers_user_read` and `bakers_conductor_list`), with the rights of its service account. Only the nightly `composer-audit` cron job has a shell (*The nightly Composer audit* below). The tools serve exactly the steps of `bb-create-ticket`, status reads, the answer path and the nightly audit. Make that account a member of the bot's project's team only: the bot acts on its project, and the account's membership is what bakers.build enforces. The container sees only Hermes' home and that clone, has no Docker socket and runs with almost every capability dropped.

## How it works

- **One container, two processes.** The image keeps Hermes' own start: its bootstrap runs as root, maps the `hermes` user to the workspace user's UID and prepares `/opt/data`, then drops to `hermes`. `entrypoint.sh` then renders `config.yaml` and `SOUL.md`, replaces the shipped skills in `/opt/data/skills` and the plugin in `/opt/data/plugins/bot-channels`, removes the retired `project-manager` skill, and runs `node poller/poller.mjs` and `hermes gateway run` side by side. When either exits, the container exits and Docker restarts it. A conversation whose turn was still running when the gateway was killed (a workspace stop, an OOM kill) is not left paused: on the requester's next message the plugin settles the lost turn as interrupted, without running it again, and the bot answers.
- **What survives a start.** `/opt/data` is on the workspace's home volume. Sessions, memories, skills the bot learned, the poller's state and the plugin's list of request channels stay; the configuration, the persona and the shipped skills come from the image every time.
- **The skills ship in the image.** `bb-create-ticket` and the recipes `bb-recipe-superpowers` and `bb-recipe-matt` come from the bakers-build repository's skill bundle (branch `next`) at the image's build revision, with every bundle file their links reach; their method skills `brainstorming` and `writing-plans` (superpowers `v7.0.0`) and `grilling` (mattpocock/skills `v1.3.2`) come unchanged from their pinned commits. Check mode prints the bundle version (`bakers skills <version>`) and the shipped skills.
- **A channel per request, no threads.** A mention of the bot at the top of its main channel (`SLACK_ALLOWED_CHANNELS`) never starts a conversation there. The `bot-channels` plugin, a Bolt middleware in Hermes' Slack app, opens a public channel `req-<first words>`, invites the sender, posts a fixed acknowledgement there that mentions them (no model call), replies flat in the main channel with a link to it, records it in `/opt/data/bot-channels.json` with the requester's Slack e-mail address (`users.info`, scope `users:read.email`) and hands the message on to Hermes as if it had been written in the new channel. If handing it on fails, the plugin asks the requester there to repeat the request. Hermes runs with `reply_in_thread: false`, so each channel is one flat conversation, and in the bot's own channels it answers without a mention. Each message from a served user in an open channel gets an `eyes` reaction while Hermes works on it, removed when it is done; no ✅ or ❌ stays behind. The plugin's fixed texts live in `plugins/bot-channels/messages.json`, in German and English (see *One language*).
- **Only its own channels.** Before each message Hermes asks the plugin which channels it serves: the main channel and the bot's open channels (the request channels in `bot-channels.json` and the poller's reopen channels in `poller-state.json`, minus the archived ones). In any other channel, even one the bot was invited to, it does not answer. Each open channel gets a trusted line before the conversation with its ID, its link and its ticket, which the model cannot see otherwise.
- **One language, German by default.** The bot's language is `PM_BOT_LANGUAGE` in its env file, an ISO 639-1 code (`en`, `fr`); the workspace template writes it like every other key. When the plugin starts, it reads the setting once, with no model call and no read on bakers.build, and logs `bot-channels: answering in <code>`. Unset or empty means German; a value that is not a two-letter code logs `bot-channels: language: PM_BOT_LANGUAGE "<value>" is not an ISO 639-1 code; answering in German` and keeps German. Every trusted line ends with that code, the main channel's line names it alone, and the persona answers in it. The plugin's own texts exist in German and English (`plugins/bot-channels/messages.json`); for any other language they stay German while the model answers in that language. The plugin shares the code with the poller in `/opt/data/bot-language.json`, writing `de` first and then the set code; the poller reads it on each pass and posts its fixed texts (`poller/messages.json`) in German or English, German for any other language. The service account's **background** on bakers.build stays the agent's profile and does not set the language. The ticket text the poller relays (a summary's Outcome, a question, a technical problem, the done post's Manual review) stays English, as ticket text is. Hermes posts no interim message in Slack (`display.platforms.slack.interim_assistant_messages: false`): the text the model writes beside its tool calls is a working note and stays out of the channel. A change applies after `docker compose -p pm-bot restart` in the workspace, without a rebuild.
- **The bot hosts the skill.** `SOUL.md` gives `bb-create-ticket` the project, workflow and conductor, the requester's name and Slack user ID from the prefix Hermes puts on each message, the channel's link from its trusted line as the conversation link, the requester's e-mail address from that line as the ticket's reviewer (never as its assignee, so the box conductor can be set and its owner becomes the assignee), and the wish to specify every request with its requester. Only the requester's "yes" hands the ticket over.
- **A review is proposed, the requester decides.** Before the approval round the bot judges whether a code review by a developer is advisable: when the request touches a dependency, the data model, a public interface, authentication, permissions, or build, CI or deployment configuration, or the requester describes such a risk. A review is charged, so the bot only proposes it, in plain words: what it is and why it recommends it for this request. The proposal does not mention the cost; the requester already knows it. On hand-over it adds `ticket-question` and one gate label: `human-accept` when no review was advisable, without a question; `human-review` when the requester accepts the review; `human-accept` and `review-declined` when the requester declines it, so the decline stays visible on the ticket. With `human-accept` a person accepts the result before it is merged; with `human-review` a developer reviews the change first. The contract (`tests/contract/pm-bot.sh`) fails when the persona or this README names the former unattended hand-over label, the persona names `human-review` outside the requester's yes to the review, or the persona tells the requester the review is charged.
- **The ticket's channel is a link.** A ticket created from Slack carries the channel's link (`https://<workspace>.slack.com/archives/<channel ID>`) titled *Slack channel*; bakers.build stores it as kind `chat`. The poller reads a ticket's conversation from its **newest** channel link; a ticket from before channels, with only a thread permalink, keeps getting its posts in that thread.
- **The poller keeps the channels.** Once a request channel's ticket exists, the poller renames the channel to `<identifier>-<title>` (`yf-12-comic-sans`, at most 40 characters, `-2` when the name is taken). When the ticket reaches `done` or `cancelled`, it posts the final state and then archives the channel. Slack does not let a bot unarchive, so when the ticket is reopened the poller opens a fresh channel (`yf-12-comic-sans-2`), invites the requester, posts the new state with a link to the archived channel and adds the fresh channel's link to the ticket. A request channel without a ticket that stays silent for a week gets a last message and is archived. Each step is recorded in `poller-state.json` before the next, so a failed step is retried and none is repeated.
- **Questions follow the ticket label protocol.** An agent asks by publishing a comment, adding the **Question** label to the ticket and freezing it. The open question is the newest comment that is not a `summary`, created at or before the ticket's `frozen_at`. The poller posts it into the ticket's channel once: through `hermes send`, which also adds it to the channel's Hermes session, or, with `SLACK_API_URL` set (a Slack API other than Slack's, which `hermes send` cannot reach), itself through that API. Anyone in the channel may answer, an approval included; the bot checks the ticket is still frozen with the label, posts the answer as a comment headed *Answered in Slack by <name> (Slack user <ID>):*, removes the label and unfreezes the ticket. A reply to a ticket labelled `technical problem` is not passed on.
- **Status updates between states.** For each open ticket the poller also reads its runs (`bakers_run_list`) and comments and posts, once each: a line when a run starts (starts within 5 minutes of the last posted one share its line); a line when a run ends without moving the ticket on, also for a run that started and ended between two passes, after its start line: *waits for a decision* for a finished one, and *paused* for a failed, expired or cancelled run, but only on the next pass and only if that pass still finds the ticket unfrozen, without a question or technical problem and in the same state (a run that asks a question is closed as cancelled when the ticket freezes, and its label can reach the list a moment later, so the paused line is decided from the ticket read after its runs, not from the list read at the start of the pass); none while a question or technical problem is open, whose relayed note says it alone; the first one or two sentences of a new `summary` comment's *Outcome*, leaving out sentences with code, ticket, AC or run identifiers, or recipe and agent names; and a new preview link (a `.ddev.site` page or a Designbook link) with its title, or without it when the title holds such words. With `PREVIEW_ZONES` set (comma list of DNS zones, e.g. `preview.keytec.de`), a new summary's Outcome is followed by each link of its *Manual review* section whose host is one label under such a zone, `https:` only, without credentials or port, once per summary and URL; no other URL of a summary is ever posted. A `.ddev.site` link opens only on the box: with `PREVIEW_ZONES` set it is left out when the same pass posted such a link for its ticket, and otherwise carries a note saying so. Without `PREVIEW_ZONES` none of this happens. While a run is running in `working` or `review` and the conversation has had no post from the poller for `PM_BOT_HEARTBEAT_INTERVAL` seconds (default 1800), it posts one *still working* line with a sentence of the newest summary since the run started. Runs, summaries and links from before the poller followed a ticket are recorded, not posted. The texts are in `poller/messages.json`.
- **Sub-tickets share their ancestor's channel.** A sub-ticket without a conversation of its own posts its states and notes into the channel of its nearest ancestor that has one, behind its identifier (`YF-13 · …`). It gets no channel and no thread.
- **One credential, no sign-in.** Hermes and the poller send the service account's API key as the bearer on bakers.build's `/mcp`; there is no token to refresh. Hermes fills the header from the env file (`${env:BAKERS_API_KEY}` in the configuration), so the key never lands in `config.yaml`.
- **Redeploys need no restart.** While bakers.build is down, a tool call fails: a poller pass fails and keeps its state file, and the next pass catches up and posts nothing twice; Hermes reconnects on its own. Hermes talks to Slack over Socket Mode, which does not depend on bakers.build.
- **It needs a bakers.build with API keys as bearer, the project ticket list tool, `bakers_user_read` and `labels_remove`** on `bakers_ticket_update`, and the service user's position and background set on its profile (the template's README › PM bot › The bot's service account).

## The nightly Composer audit

Every night the bot audits the project's Composer dependencies on a freshly pulled clone and opens a ticket when there is something to update.

- **When.** Hermes' cron scheduler, inside the gateway, runs the job `composer-audit` at `AUDIT_TIME` (default `03:30`) in the container's time zone `TZ` (default UTC). `entrypoint.sh` registers it by name on every start, so a restart keeps exactly one job; a night the container was down is caught up when it starts within two hours, and skipped with a log line when it starts later. `hermes cron list` in the container shows it.
- **Only after a pull.** The box pulls the clone at night and writes `/opt/data/clone-pulled.json` (`{ "at", "head", "ok", "error" }`; the workspace template's job, keytec/infra). The audit runs only on a marker with `ok: true` and `at` at most 24 hours old; otherwise the run's output under `/opt/data/cron/output/` says why, and nothing is posted. Until the template writes the marker, every night skips with *no pull marker*.
- **What it checks.** Every `composer.lock` with a `composer.json` beside it, outside `.git/`, `vendor/` and `node_modules/`, with `composer audit --locked --format=json --no-plugins --no-scripts --abandoned=ignore` in its directory: the installed versions against Packagist's security advisories, without installing anything or running the project's plugins or scripts. Abandoned packages are not reported.
- **What it keeps.** Nothing between nights: the open audit ticket is the only record, found each night with `bakers_ticket_search` (title `Security updates:`, not `done` or `cancelled`). A failed `composer audit` or search writes nothing and is the run's message in the main channel.
- **The ticket.** Advisories without an open audit ticket create one `chore` in the bot's project, labelled `security`, titled `Security updates: <n> Composer advisories (<packages>)`, with a table per lock file and its `composer update <packages> --with-dependencies` line. Its conductor is the project's only active conductor; with none or several, none is set and the run's message says so. It gets a request channel like a request from Slack, without a requester, and the run posts one line linking both into the main channel. While that ticket is open, every night adds one comment with the current tables, or one saying none remain; no second ticket is created. Once it is `done` or `cancelled`, the next finding opens a new ticket.
- **The shell.** The job's agent gets the toolsets `terminal`, `skills`, `mcp-bakers` and the plugin's `bot-channels-cron`; Slack's toolsets do not change. Its shell starts in the clone and runs only the commands its skill names: `cat`, `date`, `find`, `grep` and `composer audit`. `approvals.deny` in `config.yaml` refuses commands that read the env or the env file (`env`, `printenv`, `.env`, `environ`, any `$` expansion, `node -e`/`-p`/`--eval`/`--print`, `python`, `php` itself in the usual ways it is called) or reach the web with `curl` or `wget`, and `approvals.cron_mode: deny` refuses every other dangerous command at once. These globs slow a misled run down; they are no sandbox: a shell in the container can still reach `/opt/data/.env`. The skill comes from the image, and the job reads no instructions from the clone.
- **Switch it off.** Set `AUDIT_ENABLED=false` in the env file (workspace parameter) and restart: the start removes the job and logs one line. When it cannot read or remove the job, it says so instead, and the job may still run. `AUDIT_ENABLED`, `AUDIT_TIME` and `TZ` are read on every start.

## The conductor

The bot creates its tickets with the conductor `PM_BOT_CONDUCTOR` names; that conductor runs the work, wherever its machine is. It runs each agent run in a container of its own through `@bakers-build/addon-runtime-docker`, so the agent may work at `permissions: 'yolo'` inside it. Its machine configuration ([Machine](https://bakers.build/configuration/machine)) lists the two addons:

```js
// ~/.bakers/machine.config.js on the conductor's machine
addons: [
  { use: '@bakers-build/addon-runtime-docker' },
  { use: '@bakers-build/addon-claude', with: { permissions: 'yolo' } },
],
```

The conductor reads its model credentials only from `~/.bakers/.bakers.env` on its machine, mode 600, with `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`; a run gets only the keys its addons declare. The workspace provides that file; no secret is in this image or repository. `addon-runtime-docker` and the `.bakers.env` loader come with a bakers.build release after the current one; until then, the conductor's machine needs the bakers.build version that ships them.

The bot's own container stays as it is: no Docker socket, no `.bakers.env`, and the contract (`tests/contract/pm-bot.sh`) fails when `compose.yaml` adds either.

## Develop

```sh
node --test '**/*.test.mjs'     # poller, client and render, against stubs
python3 -m unittest discover -s plugins/bot-channels   # the plugin's pure core
bash tests/contract/pm-bot.sh          # lock-down of the configuration, the persona, the plugin, the build lines, the Slack app and the compose file
bash tests/contract/pm-bot-image.sh    # builds the image; check mode (plugin loaded, its Hermes seams, /mcp stub), the plugin's recovery test on Hermes, then run mode (Docker)
bash tests/e2e/run.sh                  # the end-to-end test (below; Docker)
```

Build the image from the repository root. Its skills come from three named build contexts: the bakers-build repository's skill bundle (branch `next`) and two upstream skill repositories pinned by commit (superpowers `v7.0.0`, mattpocock/skills `v1.3.2`), so building needs GitHub access:

```sh
docker build -t pm-bot:local \
  --build-context bundle=https://github.com/bakers-build/bakers-build.git#next:.claude/skills/bakers-build \
  --build-context superpowers=https://github.com/obra/superpowers.git#bb92a77741419a4ab5f06e711a283343f1ada0c3 \
  --build-context mattpocock=https://github.com/mattpocock/skills.git#d1478fcb140db0b93c0c8df17bcfd311844749d0 .
```

GitHub CI runs the first three in its `tests` job; its `image` job builds the image, smoke-tests it and runs the end-to-end test on it; the release then publishes the image to GHCR (the template's README › PM bot › The bot's version).

## End-to-end test

`bash tests/e2e/run.sh [IMAGE]` runs the bot's image against a real bakers.build site and conductor, with no Slack and no credentials, and exits non-zero naming each failed scenario. CI runs it in the `image` job on the image it is about to publish. It needs Docker and this clone; without `IMAGE` it builds the working copy (GitHub access, as above). On an arm machine the site's release images run emulated, which takes several times longer.

| Service | What it is |
|---|---|
| `pm-bot` | The image under test with production's service from `compose.yaml`: only its command (`agent`), start order and network differ, and its env file has every key of `.env.example` (`tests/contract/pm-bot.sh` checks both). Mode `agent` runs the poller and no gateway; the test talks to the bot through `hermes chat` in the container, with the trusted line and sender prefix the gateway would add |
| `nginx`, `php`, `db`, `deploy` | bakers.build from its public release images (`BAKERS_VERSION`, default `0.11.0`), seeded by `tests/e2e/seed.php`: a project, the bot's service account and key, a conductor owner and key, a requester and a conductor that takes working runs |
| `conductor` | The bakers.build CLI with a stub `claude` (`tests/e2e/conductor/`) that plays the script a scenario leaves for its ticket (`tests/e2e/agent/`): ask a question, hit a technical problem |
| `model` | A scripted Anthropic Messages endpoint (`model.base_url` from `PM_BOT_MODEL_BASE_URL`): each scenario scripts the bot's tool calls, and a call it did not script fails the scenario |
| `slack-recorder` | The Slack Web API methods the poller and the nightly audit's channel tool call (`SLACK_API_URL`), answered and recorded |
| `advisories` | A Composer repository with Packagist's security-advisories API (`tests/e2e/advisories/`), the only repository of the clone fixture (`tests/e2e/clone/`): one advisory for its locked `acme/widget` 1.0.0 |

The scenarios (`tests/e2e/scenarios/`) assert what the site and the recorder hold, never wording. `--only <scenario>` runs one scenario file, named without `.e2e.mjs` (e.g. `--only questions`), `--keep` leaves the stack running (`bash tests/e2e/run.sh down` removes it), `--real` uses a real model for the bot and Claude Code for the conductor (`ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`; a failure may then be the model's). A failed run leaves the stack's logs, the model's turns, the Slack calls, the poller's state, the advisory requests and the audit's runs in `tests/e2e/out/logs/`.

## Look at it in Hermes WebUI

For local use only: a first look at the bot's Hermes in [Hermes WebUI](https://github.com/nesquena/hermes-webui) (0.52.732, pinned by digest in `webui/compose.yaml`), without Slack and without a workspace. Several people sign in with their bakers.build account and talk to the one bot, each in their own profile and sessions. It is no deployment: `compose.yaml` and the image stay as they are, and a bot started from them serves no web UI. Its identity provider is the end-to-end test's bakers.build, and every port listens on `127.0.0.1` only.

Once, on this machine:

```sh
echo '127.0.0.1 nginx' | sudo tee -a /etc/hosts               # the site answers to the host name nginx alone
tests/e2e/run.sh ghcr.io/bakers-build/hermes-bot:main --keep --only status   # the site, seeded; leaves it running
cp webui/.env.example webui/.env                                 # then fill in PM_BOT_CLONE and the model credential
webui/register-client.sh                                         # the site's bot key, project, OAuth client and users
```

Then start and stop it:

```sh
docker compose -f webui/compose.yaml up      # then open http://127.0.0.1:8787
docker compose -f webui/compose.yaml down
```

**Sign in.** The site sends no mail, so it signs people in with a one-time link: `docker exec pm-bot-e2e-php-1 /var/www/html/vendor/bin/drush user:login --name=e2e-owner --uri=http://nginx:8788` prints one; open it, then http://127.0.0.1:8787, and allow the access. The seeded users are `e2e-owner` (owner@example.test) and `e2e-requester` (requester@example.test); a second person uses the other in a second browser.

**`webui/.env`.** You fill in the model credential (`ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`), `PM_BOT_CLONE`, the absolute path of a clone of the project, and `WEBUI_USERS`, each user's bakers.build e-mail address and own profile (`owner@example.test=owner,…`). `webui/register-client.sh` writes `BAKERS_URL`, the bot's `BAKERS_API_KEY`, `PM_BOT_PROJECT` and `PM_BOT_CONDUCTOR` from `tests/e2e/out/seed.json`, the OAuth client, a cookie secret, and `HERMES_WEBUI_GROUP_PROFILE_MAP`, the users by bakers.build user ID: the site tells the proxy nothing about a user but that ID. Run it again after changing `WEBUI_USERS` and after the site was removed (`tests/e2e/run.sh down`, or any e2e run without `--keep`): a new site knows neither the client nor the users. `PM_BOT_IMAGE` picks the bot image (default `ghcr.io/bakers-build/hermes-bot:main`). The Slack values stay inert, and `AUDIT_ENABLED=false` keeps the nightly job out. The published image is amd64 only: on Apple silicon add `DOCKER_DEFAULT_PLATFORM=linux/amd64` to `webui/.env`, and everything runs emulated.

**How it fits together.** `prepare` runs the bot image's `entrypoint.sh check` once, so the Hermes home holds the bot's config, persona, skills and plugin and has reached bakers.build's `/mcp`. `setup` installs the Anthropic and MCP packages into Hermes' dependency environment and renders one profile per user: the bot's home, plus the trusted line of a request channel that names the user as the requester, so a ticket the bot opens from their session names them as the reviewer. `oauth2-proxy` signs people in at bakers.build and passes their user ID to the web UI, which trusts it from the proxy's address alone and binds the user to their profile. `bakers-front` serves the site to the browser as http://nginx:8788. `down -v` wipes the home with its sessions, and is needed after changing or pulling `PM_BOT_IMAGE`. Run it once as well when a home from before the sign-in exists: its dependency environment lacks the MCP package. The web UI runs no clone reader (its container has no working Node).

**What stays open.** Every signed-in user reaches the web UI's terminal, workspace file browser (edit and delete), settings, cron and skills, and can edit their profile's persona and trusted line. Anyone else with an account on the site who signs in lands in the profile `default`, the bot's own home. Keep it on this machine.

## Test it by hand

On a workspace running the bot, with the service user's profile set and the Slack app reinstalled with `channels:manage`, `reactions:write` and `users:read.email`, and three people or places: the **requester**, a **second member**, and an **outsider channel** the bot was invited to but did not open. Record each step with its channel name and link and the ticket as bakers.build shows it.

1. **A channel per request.** The requester mentions the bot with a feature request in the main channel. A flat reply there links a new `#req-…` channel; the requester is in it and the bot answers there without further mentions. The main channel shows no thread.
2. **Specify and hand over.** The requester names another person and e-mail address in the request, then answers the bot's questions in the channel. The bot's reply that links the ticket names the requester as a reviewer, or says that no reviewer was added when the requester has no account in the project's workspace. The ticket's assignee is the conductor's owner. After their "yes" the ticket carries the `spec`, `plan` and `test` comments with *Approved by <name> (Slack user <ID>)*, a type and recipe, the conductor, the labels `human-accept` and `ticket-question` (a request with nothing on the review's risk list gets no review question), the state `working` and the link *Slack channel* to `…/archives/C…`. Within `PM_BOT_POLL_INTERVAL` seconds (default 15) the channel is renamed to `<identifier>-<title>`. The channel shows no English working notes beside tool calls.
3. **Only the requester's yes.** On the next request, the second member joins its channel and answers "yes" to the summary first: nothing on the ticket changes. The requester's "yes" then hands it over.
4. **A review is proposed.** Request a change to the login. Before the work starts, the bot proposes a code review by a developer and says what it is and why it recommends it for this request, without mentioning the cost. The requester accepts: the ticket carries `human-review` and `ticket-question`. Repeat and the requester declines: the ticket carries `human-accept`, `ticket-question` and `review-declined`.
5. **An answer from anyone.** Publish a `# Question` comment on the ticket, add the **Question** label and freeze it. It appears once in the channel; `docker compose -p pm-bot restart` posts no second copy. The second member answers with a plain message: the ticket gets *Answered in Slack by <name> (Slack user <ID>):* with the answer, loses the label and is unfrozen.
6. **A technical problem stays.** Publish a technical-problem note, add the label `technical problem` and freeze the ticket. The note appears once behind `The work on the "<title>" ticket is stuck on a technical problem that keytec has to solve:`, also when the ticket carries **Question** as well. Reply in the channel: nothing is written to the ticket; the bot points to the developers.
7. **Status in plain words.** Ask "how is it going?" in the channel: the bot answers with the ticket's state in plain words and two or three sentences from the latest summary. Move the ticket to `review`: the post appears once.
8. **Closing and reopening.** Move the ticket to `done`: the final post with where and how to test appears, then the channel is archived. Move it back to `working`: a channel `<identifier>-<title>-2` appears with the requester in it, a link to the archived channel and the state, and the ticket carries a second *Slack channel* link.
9. **Only its own channels.** Mention the bot in the outsider channel: no reply, and no ticket is created or changed.
10. **One language.** With `PM_BOT_LANGUAGE` unset or `de`, a request written in English gets a German reply in the main channel and German answers, and the container log shows `bot-channels: answering in de` after the start. Set `PM_BOT_LANGUAGE=en`, run `docker compose -p pm-bot restart`, and write in German: the reply and the answers are English, and the log shows `bot-channels: answering in en`. With `fr` the answers are French and the plugin's reply German. With `English` the log shows `bot-channels: language: PM_BOT_LANGUAGE "English" is not an ISO 639-1 code; answering in German`. Set it back to `de` and restart.

Also check the limits: after a restart of the bakers.build site a new request is answered without restarting the bot. A request channel without a ticket is archived after a week of silence; that takes a week, so the poller's tests cover it against stubs.

**What the end-to-end test covers.** It covers the bakers.build side of steps 2, 5, 6, 7 and 8 and both restart limits: the handed-over ticket and the rename (2), the answer written, the label removed and the ticket unfrozen (5), nothing written after a technical problem (6), the status read and the one post on `review` (7), the archive, the `-2` channel with the requester and the second link (8), no second post after a restart of the bot, and a ticket after a restart of the site. It runs the nightly Composer audit as its schedule does (`hermes cron run composer-audit`): a fresh clone opens one `security` chore with the table, its request channel and link, the next night comments on it instead of opening a second, and a pull marker older than 24 hours writes nothing and says why. It also checks that the question and the technical problem are relayed into the channel, the question once, and that a run that only asked a question is never reported as a problem. Steps 1, 3, 4, 9 and 10, the week-long archiving, the Slack side of 2 and 5 (the channel per request, the *Slack user* in the answer) and the relay through `hermes send` stay manual here; the plugin's and the poller's unit tests cover steps 1 and 9 and the attribution against stubs.

## Approve what it learns

The bot keeps no memory and writes no skill without you. Review its proposals in a Hermes session inside the container, `docker compose -p pm-bot exec pm-bot hermes`, with `/memory pending` and `/skills pending`. A lasting change belongs in this repository: in `SOUL.template.md`, or in the bundle skills, which every start replaces with the image's.

## When something fails

| Symptom | Cause and fix |
|---|---|
| `/mcp answered 401` in the container log | The API key is wrong or revoked, or its account is blocked: create a new key and update the `pm_bot_bakers_api_key` parameter |
| `Tool not found: "tool_api__…"` in the container log | The image is older than the server's tool names: the server renamed a tool the bot still calls. Rebuild the image from `main` and update the workspace's image |
| `pass failed: … 503` or `ECONNREFUSED` in the container log | bakers.build is down or redeploying; the poller retries every pass on its own |
| The bot says the labels could not be added or the channel could not be linked | The service account lacks update rights in the project: fix its rank, then add the label or link by hand |
| `Ich konnte keinen Kanal für diese Anfrage eröffnen` (`I could not open a channel for this request`) in the main channel, `bot-channels: request channel …` in the container log | The Slack app lacks `channels:manage` or the workspace forbids creating channels: add the scope, reinstall the app |
| `rename …`, `archive …` or `reopen …` with a Slack error in the container log | The poller retries every pass; `missing_scope` means the app lacks `channels:manage` |
| `bot-channels: no e-mail address for …` or `Slack returns no e-mail address for …` in the container log, tickets without a reviewer | The Slack app lacks `users:read.email` (reinstall it with the scope), or Slack hides the address (Slack Connect, a hidden profile field); the ticket is created without a reviewer |
| No `eyes` on messages in a request channel | The Slack app lacks `reactions:write` (Hermes logs the failed `reactions.add` at debug level only): add the scope, reinstall the app |
| The bot does not answer in a channel | It answers only in its main channel and the request channels it opened and has not archived; a channel it was merely invited to stays silent |
| `bot-channels: language: PM_BOT_LANGUAGE "…" is not an ISO 639-1 code` in the container log, the bot German | The setting holds no two-letter code: set `PM_BOT_LANGUAGE` to one (`en`, not `English`), then `docker compose -p pm-bot restart` |
| The nightly audit posts nothing; the job's output under `/opt/data/cron/output/` says *no pull marker* or *no pull in the last 24 hours* | The box did not pull the clone that night: check the workspace template's nightly pull and `/opt/data/clone-pulled.json` |
| `Composer audit failed: …` or `cannot search for the audit ticket` in the main channel | `composer audit` could not read a lock file or reach Packagist; nothing was written and the next night tries again |
| `pm-bot: AUDIT_TIME must be HH:MM` | `AUDIT_TIME` is not a time like `03:30` |
| `pm-bot: missing: …` and the container restarting | The env file lacks a required key; check the workspace's skip line and parameters |
| `pm-bot: SLACK_ALLOWED_CHANNELS must name exactly one channel` | `pm_bot_slack_allowed_channels` lists more than one channel; the bot has one main channel |
| `render …: … may hold only …` | A parameter holds a character the configuration cannot take safely |
| A relayed question or technical problem never appears | The ticket has no `chat` link, lacks the **Question** or **technical problem** label or is not frozen; `hermes send exited …` (or, with `SLACK_API_URL` set, `chat.postMessage failed: …`) in the container log names the Slack error |

## Cut it off

- **Stop it:** `docker compose -p pm-bot down` in the workspace, or empty its parameters so no start brings it back.
- **Cut its access:** delete the service account's API key or disable the account. The next tool call of the bot and the poller is refused.

## Ticket-link smoke test

On an allowed PM-bot box, use a served Slack user to create a request. Check that the first reply links the ticket’s identifier and title using the returned canonical URL. With a stored origin, check its labelled line: HTTP(S) is clickable, other values are plain text; without an origin there is no line.

Cause a technical problem and a paused run, then finish the ticket. Each message must link that ticket and show its own origin. Repeat with a sub-ticket sharing its parent’s channel or thread: keep the identifier prefix and link the sub-ticket. Poll again and restart the poller: no duplicate messages. Refuse the done post once: the channel stays open until the retry succeeds, then archives. No message is pinned and no additional Slack scope or reinstall is needed.
